# ChartBreaker — Observability Guide

This document explains where to look to answer "what is the platform
doing?" — during a run, after a run, and when investigating a single
finding. It also calls out what is **not** observable today and
recommends follow-up work to close those gaps.

---

## TL;DR — four signal layers

| Layer | Where | When to use |
|---|---|---|
| **Stdout** | The terminal you launched `chartbreaker` from | Watch a run progress in real time. One-line summaries per attempt + verdict. |
| **Python logging** | stderr (live) — `--verbose` flag enables DEBUG | Diagnose HTTP failures, parse errors, LLM dispatch errors. |
| **SQLite + JSONL store** | `observability/runs.sqlite`, `observability/traces.jsonl` | Source of truth. Every state transition lands here. Survives across runs. |
| **Streamlit dashboard** | `streamlit run chartbreaker/observability/dashboard.py` → `localhost:8501` | Read-after-run aggregates: coverage, verdicts, severities, cost, agent timeline. |

Live tail: the JSONL mirror is append-only, so `tail -f observability/traces.jsonl` shows every agent event as it happens.

## Layer 1 — Stdout (live during a run)

When you run `chartbreaker run-mvp-loop`, you see one block per campaign:

```
[injector] Cat 1b — Indirect injection via chart text
  [injector-cat-1b] subcat=a3b9c2d1... verifier=fail semantic=fail severity=high action=regression
    pinned to regression suite as AF-REG-2026-05-11-001
```

This tells you, for each campaign:
- Which specialist owns it (`[injector]`, `[cracker]`, `[saboteur]`, `[smuggler]`, `[conversationalist]`)
- Which subcategory and the Orchestrator's rationale
- The Judge's verifier and semantic verdicts
- Whether the attempt got pinned to the regression suite

What stdout does **not** show: the actual prompt sent, the target's raw response, the LLM-side cost, or anything from non-attempt events (run-start/end, mid-turn refreshes).

Enable `--verbose` for DEBUG-level Python logs in the same stream — useful when HTTP calls or LLM parses fail.

```bash
chartbreaker run-mvp-loop --verbose
chartbreaker run-mvp-loop --semantic-judge --verbose   # also enable the LLM Judge
```

## Layer 2 — Python logging

Every module uses `logging.getLogger(__name__)`. By default the CLI installs an `INFO`-level handler that prints to stderr. `--verbose` drops it to `DEBUG`.

Where to look for specific signals:

| Signal | Logger | Level |
|---|---|---|
| Target HTTP request failure | `chartbreaker.target_client` | WARNING / ERROR |
| LLM dispatch retry on 5xx / 429 | `chartbreaker.llm_client` | WARNING |
| Specialist parse errors (LLM returned bad JSON) | `chartbreaker.agents.specialists.*` | WARNING |
| Judge semantic-call fallback to deterministic | `chartbreaker.agents.judge_agent` | WARNING |
| SQLite write or schema-migration warnings | `chartbreaker.observability.store` | WARNING |

Logs are **not** persisted to a file by default — only to stderr. To capture them automatically, use **P2.5-T6**'s `--log-file` flag:

```bash
chartbreaker run-mvp-loop --verbose --log-file           # auto path: observability/run-<run_id>.log
chartbreaker run-mvp-loop --verbose --log-file my.log    # explicit path
```

The flag attaches a DEBUG-level handler for the duration of the run and detaches it cleanly on exit. Equivalent shell redirect if you prefer:

```bash
chartbreaker run-mvp-loop --verbose 2> observability/run-$(date +%s).log
```

## Layer 3 — SQLite + JSONL store (source of truth)

`observability/runs.sqlite` holds every state transition. The schema lives in `chartbreaker/observability/schema.sql`. Nine tables plus `schema_version` (currently 3):

| Table | One row per | Key fields |
|---|---|---|
| `runs` | CLI invocation | `run_id`, `cli_command`, `operator`, `target_version`, `started_at`, `ended_at` |
| `campaigns` | Orchestrator decision | `campaign_id`, `subcategory_id`, `seed_case_id`, `rationale`, `max_cost_usd` |
| `attempts` | AttackAttempt generated by a specialist | `attempt_id`, `specialist`, `prompt`, `chart_text_payload`, `multi_turn_sequence`, `http_request` (JSON) |
| `target_responses` | Co-Pilot reply to an attempt | `http_status`, `raw_model_output`, `post_verifier_output`, `latency_ms`, `audit_log_id` (JSON of PHP verifier verdicts), `response_cookies`, `set_cookie_headers` |
| `judge_verdicts` | Judge ruling on an attempt | `verifier_replay`, `semantic`, `severity`, `rationale`, `recommended_action` |
| `findings` | Scribe-drafted vuln report (Phase 2.x) | `finding_id`, `body_markdown`, `promoted_to_published` |
| `costs` | LLM call telemetry | `agent`, `provider`, `model`, `prompt_tokens`, `completion_tokens`, `usd` |
| `agent_events` | **The timeline.** Every state transition writes one row here. | `agent`, `event_type`, `payload` (JSON), `run_id`, `campaign_id`, `attempt_id` |
| `proposed_campaigns` | Human-approval queue entry (Phase 4) | `proposal_id`, `subcategory_id`, `specialist`, `seed_case_id`, `mutation_budget`, `rationale`, `priority_score`, `est_cost_usd`, `status` (`proposed`/`approved`/`rejected`/`executed`), `decided_at`, `decided_by`, `rejection_reason`, `run_id` |

`observability/traces.jsonl` is the same agent-events stream as an append-only JSONL mirror, plus `cost_recorded` rows (which are not in `agent_events` to keep the timeline readable). Format:

```json
{"ts":"2026-05-11T19:45:01.234Z","run_id":"...","agent":"injector","event":"attempt_generated","attempt_id":"...","campaign_id":"..."}
```

### Live-tail recipes

Watch every agent action as it happens:
```bash
tail -f observability/traces.jsonl | jq -c '{ts,agent,event,attempt_id}'
```

Watch only Judge verdicts arrive:
```bash
tail -f observability/traces.jsonl | jq -c 'select(.event=="verdict_recorded")'
```

### Ad-hoc SQL — common questions

What did the platform attempt in the last run?
```sql
SELECT a.subcategory_id, a.specialist, j.verifier_replay, j.semantic, j.severity
FROM attempts a
JOIN campaigns c ON c.campaign_id = a.campaign_id
JOIN runs r ON r.run_id = c.run_id
LEFT JOIN judge_verdicts j ON j.attempt_id = a.attempt_id
WHERE r.run_id = (SELECT run_id FROM runs ORDER BY started_at DESC LIMIT 1);
```

Drill into one attempt — full prompt + target response + verdict:
```sql
SELECT
  a.subcategory_id, a.specialist,
  a.prompt, a.chart_text_payload, a.multi_turn_sequence, a.http_request,
  tr.http_status, tr.latency_ms, tr.raw_model_output, tr.audit_log_id,
  j.verifier_replay, j.semantic, j.severity, j.rationale
FROM attempts a
LEFT JOIN target_responses tr ON tr.attempt_id = a.attempt_id
LEFT JOIN judge_verdicts j ON j.attempt_id = a.attempt_id
WHERE a.attempt_id = 'PASTE-ATTEMPT-ID-HERE';
```

Timeline of one run, in chronological order:
```sql
SELECT created_at, agent, event_type, payload
FROM agent_events
WHERE run_id = 'PASTE-RUN-ID'
ORDER BY created_at;
```

Most expensive agents this week:
```sql
SELECT agent, COUNT(*) AS calls,
       SUM(prompt_tokens + completion_tokens) AS tokens,
       ROUND(SUM(usd), 4) AS usd
FROM costs
WHERE created_at > date('now', '-7 days')
GROUP BY agent
ORDER BY usd DESC;
```

Open the DB interactively:
```bash
sqlite3 observability/runs.sqlite
```

## Layer 4 — Streamlit dashboard (P2-T11)

```bash
streamlit run chartbreaker/observability/dashboard.py
# → http://localhost:8501
```

The dashboard answers the rubric's observability questions from `runs.sqlite`. Local-only by design — ChartBreaker has no public surface.

### What the dashboard covers

| Panel | Question it answers |
|---|---|
| Summary cards | Did this run produce anything? How costly was it? How broad was coverage? |
| Per-category coverage | Which subcategories did we touch, and how many attempts each? |
| Verifier replay vs semantic mix | Where did the two halves of the Judge agree/disagree? |
| Severity distribution | How dangerous were the findings? |
| Open vulnerabilities | Which attempts the Judge wants pinned for regression. Joined to specialist + subcategory for context. |
| Cost by agent | Where the dollar went per run. |
| Agent activity timeline | Heatmap of events × agents — "what did the orchestrator do? what did the judge do?" |
| Raw runs table | All historical runs, expandable. |
| **📋 Plan Next Run** tab (Phase 4) | Review, edit, approve/reject the Orchestrator's proposed slate of next campaigns. Click **Generate proposals** to populate; per-row mutation-budget edits persist to SQLite immediately; checked rows + **Launch approved batch** runs only the approved subset through the existing `_run_one_brief()` path. Pending proposals survive `streamlit run` restarts via the `proposed_campaigns` table. See `docs/spec.md` and `chartbreaker/orchestrator/proposal_harness.py`. |

Run picker in the sidebar filters every panel to one run or "All runs."

### What the dashboard does NOT cover (gaps — most now closed by Phase 2.5)

1. **~~Per-attempt drill-down.~~** ✅ Closed by **P2.5-T1**. Click the `🔍 detail` link in the open-vulns table, or visit `?attempt_id=<id>` directly. The detail page shows attack input + target response + PHP verifier verdicts + Judge rationale + cost rows + per-attempt event timeline on one screen.
2. **~~Live / streaming view.~~** ✅ Closed by **P2.5-T3**. The "📡 Live activity" tab polls the latest 50 `agent_events` and reloads every 2 seconds via HTML meta-refresh. Open it in a side tab during a run; click any event's `attempt_id` to jump into its drill-down.
3. **~~LLM request / response payloads.~~** ✅ Closed by **P2.5-T2**. `chartbreaker run-mvp-loop --trace-llm-io` writes every `chat()` call's full request + response (with token counts, latency, cost) to `observability/llm-trace-<run_id>.jsonl`. Off by default to avoid disk bloat. Grep / jq friendly.
4. **~~Inter-agent communication detail.~~** ✅ Closed by **P2.5-T4**. The timeline panel is now a chronological event feed with each `agent_events.payload` JSON foldable inline; the old bucketed bar chart is preserved inside an "Aggregate event counts" expander. Filter by agent; cap the visible list at the last N events.
5. **~~Search across rationales.~~** ✅ Closed by **P2.5-T5**. Sidebar "Search rationales" text input — case-insensitive substring match. Filters the verdict-mix, severity, and open-vulns panels live.

Remaining minor gaps:
- The semantic-Judge prompt is captured only when `--trace-llm-io` is on. Same for specialist LLM prompts. Cost rows always persist regardless.
- The dashboard timeline shows the last N events per run; for full historical replay use the SQL recipe below.

## How to investigate a specific failing attempt — recipe

1. Find the attempt in the dashboard's **Open vulnerabilities** table, copy its `attempt_id`.
2. Pull the full row via the drill-down SQL query above.
3. If the prompt is a multi-turn sequence, `attempts.multi_turn_sequence` holds the JSON array — each entry was sent in order (turn 1 = `briefing`, turns 2+ = `followup`).
4. `target_responses.raw_model_output` is what the Co-Pilot's PHP verifier saw; `target_responses.post_verifier_output` is what a clinician would see. Disagreement between the two is a finding signal.
5. `target_responses.audit_log_id` is JSON of `{source_verification, domain_verification, llm_status, failure_reason, allowed_source_ids}` — the PHP verifier's own verdict + the source-ID set it used.
6. `judge_verdicts.rationale` includes the deterministic Judge's findings plus, if semantic Judge ran, a `SEMANTIC (verdict): rationale` suffix and a `DISAGREEMENT` tag when the two halves disagreed.
7. Cross-reference `costs` rows with `attempt_id = ?` to see the LLM-side spend on this attempt.
8. Pull the full event timeline for this attempt:
   ```sql
   SELECT created_at, agent, event_type, payload
   FROM agent_events
   WHERE attempt_id = 'PASTE-ATTEMPT-ID'
   ORDER BY created_at;
   ```

## Suggested follow-up work

Phase 2.5 closed the five originally-documented gaps (T1 drill-down, T2 LLM trace, T3 live tab, T4 timeline detail, T5 rationale search) plus added run-log auto-capture (T6). Possible next steps if more observability investment is wanted:

1. **Orchestrator + RedTeamLead narration (P2-T12 — deferred).** Each routing decision writes a human-readable rationale to `agent_events.payload`, which then renders in the P2.5-T4 timeline panel. The panel already supports inline JSON payload display, so the value lands the moment narration ships.
2. **Verdict-disagreement panel.** Today the rationale carries a `DISAGREEMENT` tag when semantic and verifier_replay disagree. A dedicated panel that lists those rows separately would highlight the platform's marquee finding type without requiring rationale search.
3. **Run comparison view.** Side-by-side coverage/severity for two selected runs, so "did the fix help?" is a one-screen answer rather than two tabs.
4. **Persist Judge LLM prompts to SQLite.** Currently captured only when `--trace-llm-io` is on. A small column on `judge_verdicts` could store the rendered Judge prompt for every run.

None of these are blocking — Phase 2.5 already covers the operator-quality needs called out in the rubric.
